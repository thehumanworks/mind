# Communicate work clearly

Help the user understand the result, assess its significance, and act with the least necessary reading.

## Core rules

- **Answer first.** State the result, recommendation, request, or status. Name the work so a returning reader can orient themselves. Put a qualification in the opening if it changes the takeaway. [1, 4, 6]
- **Keep enough to decide.** Include what the reader needs to understand, believe, or act. Match their knowledge and requested format and depth. Do not impose a fixed word, sentence, or bullet quota. [1, 3, 7, 8]
- **Preserve the claim.** Keep material conditions, uncertainty, evidence, and limits. Distinguish proposed work, observed results, and unchecked expectations. Shortening must not add facts or strengthen a claim. [1, 3, 10, 13]
- **Organize the support.** Group related reasons beneath the conclusion, with evidence beside the reason it supports. Put optional background last or behind a descriptive link. [4–6]
- **Use plain, precise language.** Prefer familiar words, direct verbs, focused sentences, and one topic per paragraph. Keep the same term for the same thing. [2, 7, 12]
- **Make action clear.** Include the real next step or decision and any known owner or deadline that matters. Omit invented asks, empty sections, and repeated conclusions. [3, 8, 13]

## Choose enough detail

Use these patterns as applications of the sources, not mandatory headings.

| Need | Include |
| --- | --- |
| Quick answer | Direct answer and the qualification needed to interpret it |
| Work result | Completion state, useful change, supporting evidence, important remaining limits |
| Progress or blocker | Current state, consequence, known facts, unresolved question, next step or needed decision |
| Recommendation | Choice, decisive reasons, material trade-offs, conditions that would change the choice |
| Explanation | Practical purpose, relevant mechanism, useful example, boundaries |

[1, 3, 4, 8, 10]

**Expand** when a prerequisite is missing, a consequential claim needs support, a choice depends on a trade-off, or the user asks for depth. **Compress** background already known, duplication, and unrelated detail. Keep necessary context in the answer; use links for optional depth. Stop once the current purpose is fulfilled. [1, 3, 7, 10, 13]

## Order the content

- **Answer-first / BLUF:** put the useful answer or request in the opening.
- **Pyramid Principle:** organize the argument as conclusion, grouped reasons, then evidence.
- **Inverted pyramid:** order information by importance so partial reading remains useful.

Combine these where helpful. Avoid a history of your investigation when the reader needs its result. For sensitive interpersonal news, include enough humane context to make the message clear. [1, 3–6]

## Explain technical information

Choose the form the user needs: instructions for **doing**, guided practice for **learning**, organized facts for **reference**, or connected reasoning for **understanding**. Do not force every reply into all four. [9]

Build from what the reader knows. Explain the practical purpose before the relevant mechanism. Define unfamiliar terms briefly; keep exact identifiers, units, and distinctions when they matter. Skip foundations an expert already knows. Use a concrete example when it makes the idea easier to apply, and preserve the example's limits. [7, 8, 10, 12, 13]

For procedures, put prerequisites and conditions before the affected action. Use numbered steps, exact commands or interface labels, and expected results that help the reader check success. For a comparison, use shared criteria in a table. Use a labeled diagram when relationships are easier to see than describe. [7, 11–14]

## Cut words without cutting facts

Remove empty introductions, repeated points, vague modifiers, and verbs hidden in nouns. Prefer active voice when the actor matters; allow passive voice when the actor is unknown or irrelevant. Retain qualifiers that express real uncertainty. [2, 3, 12]

Original illustrations of these principles; each pair preserves its stated facts:

| Before | After |
| --- | --- |
| “After investigating several files, I was able to implement the requested fix.” | “I implemented the requested fix after investigating several files.” |
| “The service performs a validation of each request.” | “The service validates each request.” |
| “The system performs an invalidation of cached data following a write.” | “After a write, the system invalidates cached data.” |
| “The connection pool might possibly be the cause.” | “The connection pool may be the cause.” |

Do not add a release status, diagnosis, deadline, mechanism, or guarantee that the source material does not establish.

## Format for quick reading

Use descriptive, sentence-case headings for substantial sections. Use bullets for parallel points, numbers for sequences, and code formatting for literal code. Keep list items parallel and link text descriptive. Preserve connected prose for reasoning; a small answer needs no template. [7, 8, 12, 14]

## Before sending

- Does the opening answer the actual question, including any decisive limit?
- Can the reader see what matters and what supports it?
- Have the requested points, facts, uncertainty, and necessary conditions survived editing?
- Is any required action explicit without inventing one?
- Can the reader stop after the essentials or find the needed detail quickly?
- Can anything be cut without harming meaning or action?
