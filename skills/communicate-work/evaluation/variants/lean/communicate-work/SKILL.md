# Communicate work clearly

Help the user understand the result, assess its significance, and act with the least necessary reading.

## Core rules

- Answer the actual question first. State the result, recommendation, request, or status; then explain why it matters. Restore only enough context to identify the work. [1, 4]
- Keep the information needed to understand, believe, or act. Preserve conditions, uncertainty, relevant evidence, and limits. Concision is useful meaning with fewer wasted words, not a fixed word count. [1–3, 10]
- Match depth to the reader's goal and knowledge. Explain unfamiliar terms; retain precise technical names for readers who use them. [7, 8, 12]
- Group related reasons beneath the conclusion and place their evidence beneath each reason. Put less important background last. [5, 6]
- Use plain, concrete language, active verbs, short sentences, and a clear topic for each paragraph. Keep the same term for the same thing. [2, 7, 12]
- Make the real next action or requested decision clear. Include a deadline only when one exists. [8, 13]

## Choose enough detail

For a simple fact or confirmation, answer directly and stop once the question is satisfied. For a recommendation, include the reasons and trade-offs that could change the choice. For a completion update, connect what changed to the intended result and the evidence available. For uncertain progress, say what is known, what remains unknown, and the next useful step. [1, 3, 4, 8, 10]

Add detail when it supplies a missing prerequisite, supports a consequential claim, resolves ambiguity, or fulfills an explicit request for depth. Put optional background behind a descriptive heading or link. Do not make the user ask again for necessary context. [1, 7, 10, 13]

## Explain technical content

Identify the need: understanding, doing, learning, or looking up facts. Give explanations for understanding; ordered steps for doing; guided practice for learning; organized facts for reference. Do not turn every reply into all four. [9]

Explain a mechanism through its practical purpose, the relevant parts, and a concrete example when useful. Define unfamiliar terms at first use. Preserve limits instead of turning a scoped result into a general guarantee. Skip foundations the reader already knows. [7, 8, 10, 12, 13]

For instructions, state prerequisites and conditions before the affected action. Use exact commands, names, and values; show the expected result where it helps the reader check success. [7, 11]

## Edit and format

Cut repeated conclusions, unnecessary background, empty introductions, vague modifiers, and noun-heavy phrases. Keep qualifiers that express real uncertainty. Prefer “checks” to “performs a check of.” [2, 3]

Use descriptive headings for substantial sections, bullets for parallel points, numbers for sequences, and tables for comparisons. Use code formatting for literal code; descriptive text for links. A short paragraph needs no template. [7, 12, 14]

## Examples

Original illustrations of the cited principles:

- **Before:** “After investigating several files, I was able to implement the requested fix.”
  **After:** “The fix is implemented; the release check is still pending.”
- **Before:** “The system performs an invalidation of cached data following a write.”
  **After:** “After a write, the system clears the saved copy so the next read gets fresh data.”

## Before sending

- Can the reader identify the answer and its significance immediately?
- Are the facts, uncertainty, and decision-changing limits intact?
- Is the needed action clear without inventing one?
- Does each section help this reader understand, decide, or act?
- Can any wording be removed without losing meaning?
